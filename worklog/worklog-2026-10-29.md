## Order desk: verification step before shipment

`src/components/admin/orders/order-desk.jsx`, new `order-verification-dialog.jsx`

The legacy PHP admin (`edit_order.php`) opens an "Order Verification" modal — WhatsApp / Call / SMS confirmation panels, a remarks box, Accept/Reject — before Process Order hands off to courier selection. The Next.js order page skipped straight to the Create Shipment dialog. Rebuilt the same two-step flow:

- **Process Order** now opens `OrderVerificationDialog` first (order reference, customer, shipping address, the four confirmation panels, a remarks box).
- **Accept Order** marks every line `Accepted` (reusing the existing `changeLineStatusAction`, the same call the standalone Reject button already used), then opens the Create Shipment dialog.
- **Reject** inside the dialog marks lines `Rejected` and closes it. The original standalone "Reject Order" button is untouched, for a quick reject without going through verification.
- The WhatsApp/SMS "send" buttons and the two "Cancel Order" buttons are disabled placeholders with an explanatory tooltip — wiring real sends needs the AiSensy campaign name and RapidSMS template the legacy system uses, which isn't available in this repo. Call-status dropdowns are local-only for the same reason.

## "View" action on every resource table

`src/components/admin/resource/resource-page.jsx`

Resource list pages (orders, b2b orders/buyers, products, vendors, customers, returns, payouts, support, CRM leads, catalog, …) relied on the first column linking to the row's detail page, with no explicit action in the row menu. Added one line that injects a `View` row action wherever a resource defines `rowHref`, so every list with a detail page gets it automatically — no need to touch each of the ~15 resource config files. Resources with no detail page are unaffected.

## Responsive tables, pass one: card fallback below a shared breakpoint

Two problems, same root cause: tables with too many columns to fit a phone, and (separately) a few of them still side-scrolling at tablet/laptop widths because the switch point was too low.

- **Order detail page** (`order-desk.jsx`): the line-items table (15 columns) and the "Pricing & Tax at shipment" table (17 columns) are now card-only at every screen size — too wide for any sensible breakpoint — with each card's field grid widening itself (2 → 3 → 4 → 5/6 columns) as the screen grows.
- **Shared `DataTable`** (`src/components/data-table/data-table.jsx`): the table/card switch point moved from `md` (768px) to `xl` (1280px), fixing every resource-driven list page at once.
- **28 hand-rolled tables** outside the shared component — B2B/bulk order & quotation forms (editable line items, inputs preserved), bulk orders/quotations/shipments, payment attempts, Shiprocket/shipments tables, the courier-selection dialog, CRM team performance and customer drill-down, the shared marketing data-grid, expenses manager, script/SEO/trend sections, CMS redirect dialogs, pricing cost-management, the return-request item picker — converted to the same card-below-`xl` pattern. Four were deliberately left as desktop-only tables: order report and payout-items (dense CSV-style exports with per-column header filters), the delivered-orders table (same reason), and the seller-agreement modal (its tables are printable legal-document content, not a data grid).
- **Main Dashboard filter bar** (`dashboard-filters.jsx`): the date-range inputs now stack vertically below `sm` instead of clipping, and the More filters / Reset / Apply filter row wraps instead of running off-screen.

All of the above is in `fd67b1c`, pushed.

## Responsive tables, pass two: two stragglers, then the real decision

A follow-up screenshot at 1024px showed the "Latest orders" list on the Main Dashboard still scrolling — `MiniTable` (`range-switch.jsx`) and the marketing engagement tracker (`engagement-section.jsx`) both already had a card fallback from before today, so pass one's sweep skipped them as "already fine" without checking they'd been left on the old `md` switch point. Both moved to `xl` to match everything else. *(Uncommitted.)*

Then, on the main `/admin/orders` list specifically — a 5,549-row grid with sorting, per-column filters and bulk actions — the table was still wide enough to scroll sideways even on a full desktop screen, which is normal for a dense power-user grid but not what was wanted here. Decision: cards everywhere, including desktop, for every table the shared `DataTable` drives. Rewrote the component:

- Removed the desktop `<table>` rendering path entirely; the card/list view is now unconditional at every width.
- Column filters (previously small funnel icons in each table header, used only by the Orders list) moved into a toggleable "Column filters" panel above the list — same filter popovers as before, just relocated, so nothing was lost.
- Sorting stays on the dropdown the card view already had; removed the now-dead header sort-button code and an unused `dense` prop no caller ever set.
- The per-row field grid widens itself on larger screens (2 → 3 → 4 → 6 columns) instead of staying cramped at two columns on a desktop monitor.

This touches every resource-driven list page in the admin app at once. *(Uncommitted at time of writing — `range-switch.jsx`, `engagement-section.jsx`, `data-table.jsx`.)*

## Note: a concurrent-edit stash recovery

Pass one's file-level work was split across four parallel passes touching disjoint files. One of them ran `git stash`/`git stash pop` mid-task against the shared working tree to diff against a clean baseline, without accounting for the other three editing the same tree concurrently — the pop conflicted with a sibling's live edit to `script-section.jsx`. Recovered by restoring every other stashed file individually and leaving that one alone for its own pass to finish. Verified afterward: `git status` showed every expected file from all four passes, nothing missing, and the leftover stash's content was confirmed to be a strict subset of what ended up in the working tree before it was dropped. No data lost; flagging it here as the kind of thing to watch for if running sub-passes against a shared repo again.
